# PULSE 单仓库、统一运行布局与持续部署方案

状态：**原方案 PR #466 已合并；本文维护当前目标与实施边界，不宣告整体迁移完成。**

关联：`wi_20260823_184`。现状、证据时间及未验证对象统一见[实施盘点](pulse-platform-deployment-inventory.md)；历史方案和实施过程保留于 Git、原 PR 与 Issue #550，不把旧断点当作当前故障。

本方案替代旧 CR-02 的“全部运行数据物理迁入 Git 仓库”和通用迁移授权系统路线。已确认的要求仍是：**迁移是一次性的，部署脚本不是；已更新模块必须能够自动构建、部署到正确位置，且重启后仍可用。** 持续部署能力属于实施交付物，不是迁移完成后的可选工作。

本轮排除 Platform；Stats/ComputeCost 仅核对迁移读取接缝，业务修复和自身发布由原负责人承担。已完成的源码历史导入、PULSE 账本读者切换、Relay 配置/状态迁移及用户确认的通信恢复不重做。两云旧稳定入口先单独收敛，不以此宣布其余物理布局完成。Vultr 37 条 cron 保持禁用。

按已确认计划逐步执行，每步结束暂停并复核下一步。文档和隔离验证不授予生产路径写权；生产切换、自动发布启用、整机重启及不可逆清理仍需精确维护范围。正式验收定义中的旧 Platform 描述须通过原生命周期入口对齐，不手改 `.harness`、指纹或历史凭据。

## 1. 一句话目标与交付边界

本轮适用的 PULSE 模块从 PULSE 一个仓库构建发布，在每台机器的固定平台根中运行；迁移完成后，受批准范围内的更新通过长期维护的部署入口自动完成构建、安装、必要重启与验证，不再靠人工复制、临时环境变量或 CWA 中的旧 Harness 部署维持运行。Platform 不纳入本轮实施或验收。

| 工作 | 生命周期 | 交付及边界 |
| --- | --- | --- |
| 旧仓、旧根、账本发布权和工作现场迁移 | 一次性、有人值守 | 盘点、隔离验证、批准维护、无损切换、旧入口退役；不开发通用搬迁/迁移签发/自动续跑系统 |
| 构建、部署、启动、升级与程序回退 | 长期、可重复 | PULSE 内的部署脚本、Actions、模块/节点映射、服务模板及测试；日常升级不重走一次性搬迁步骤 |
| 备份与灾备恢复 | 长期 | 保全持久数据、配置、信任材料及匹配程序；恢复后由相同部署入口接回服务，不依赖本次操作者的记忆 |

单仓库不等于把数据库、密钥提交 Git；统一管理不等于共用数据库或权限身份。同一业务账户的 Python 消费者复用 Coevolution `ssot/toolchain` 声明的唯一环境，不建立项目、uv tool 或每发布一份的长期 Python 环境。一次性工作不建迁移平台，**不意味着部署只能人工操作，也不意味着部署脚本在迁移后删除。**

## 2. 唯一源码与协作权威

- 唯一平台仓库：`bigbird-online/PULSE`。源码、测试、依赖声明/锁定、部署脚本、服务与配置模板、备份/恢复说明和 CI 都在这里。
- 批准的源码根同级目录是 `Relay/`、`agent-harness/`、`Stats/`、`ComputeCost/`、`Platform/`；`ops-doc/`、`skills/` 与 `_archived/` 也同级保留。不得保留内层 `PULSE/Bigbird/` 作为源码目录；外层业务目录 `Coevolution/Bigbird/PULSE` 仍是有效仓库位置。该源码重构尚未部署或完成 UAT，不能据此改写已观察到的生产物理路径。
- Harness 可发布的协作记录及策略归 PULSE `.harness/`，保全相关历史、原 ID 和已有证据；同路径冲突不得覆盖。只保留一个发布权威，服务 checkout 与人类 checkout 不混用。
- CWA 保留自身业务、历史、工作树和 Coevolution 上位治理；旧 CWA Harness 源码、安装和账本退出 PULSE 的构建、启动、发布与恢复依赖。共享 Python/Node 及工具链声明是明确的外部依赖，不是旧 Harness 安装，也不在本 WI 另造一套提供者。
- 平台运行必需、目前仍由 CWA 提供的校验器、脚本或策略也须盘点并明确归属；不能只移动 Python 模块就声称单仓完成。不顺带搬走整个 Coevolution 知识库。
- 既有旧 PR 和未提交代码保留来源。本方案不采纳未完成的新迁移签发协议，也不要求继续完善该协议作为实施前提。

## 3. 统一物理布局

`PULSE_HOME` 在本文中是目标平台根的称呼，**不是已经生效的环境变量或注册记录**。建议 macOS/Linux 均使用运行账户的 `~/.local/share/pulse`；实施时展开成该节点唯一的绝对路径并登记。该路径必须位于所有 Git 根之外，不能是 task worktree、源码 checkout 或某次 release。部署者和服务用户不同时，不得从 runner 的 HOME 猜测目标根。

```text
PULSE 源码仓库/                       # 开发/构建来源；不是生产数据根

PULSE_HOME/                           # 本机固定平台根，不进 Git
├── runtime/
│   ├── releases/<发布标识>/          # 完成构建并校验后不可变的发布集合
│   │   ├── manifest                 # 源码、模块/依赖/产物摘要及兼容要求
│   │   ├── relay/                   # 程序与该模块的运行依赖
│   │   ├── harness/
│   │   ├── stats/
│   │   ├── compute-cost/
│   │   └── platform/
│   ├── current                      # 选中的发布集合；不等于进程已全部采用
│   └── previous                     # 前一集合；不自动保证可回退
├── data/
│   ├── harness/                     # kernel、账本本机事务、注册及 WI 工作现场
│   ├── relay/                       # 会话、投递与恢复等持久状态
│   ├── stats/                       # 需保留的观测历史、采集状态
│   ├── compute-cost/                # 需保留的计量记录与处理状态
│   ├── platform/                    # 平台模块自己的持久状态
│   └── deployment/                  # 小量部署/恢复记录；不是新增常驻服务
├── config/<模块>/                   # 本机实际配置及部署映射，不含秘密正文
├── secrets/<模块>/                  # 密钥、凭据与信任记录；不只保留 key 文件
├── logs/<模块>/
├── cache/<模块>/                    # 已证明可重建的缓存
├── backups/                         # 本机恢复副本；另配独立故障域备份
└── service-repositories/            # 已登记的专用服务 checkout，不是另一源码权威
```

模块数据分类是目标职责，不是已核实的文件清单；不要求每个模块都创建所有目录。持久队列、未提交成果、授权记录、采集游标不能因“临时”或“缓存”命名被删除。工作区仍按既有分配、容量准入和登记合同管理；目录图不是创建或搬移 worktree 的授权。

每台机器采用同一约定，但分别保存本机数据库和事务。Git 账本按唯一权威发布同步；本地 SQLite 不通过 Git 或双向文件同步合库。

### runtime 与数据边界

- runtime 保存可重建的程序代码、Node 项目依赖及必要启动包装。Harness 发布保存代码、启动器和清单，Python 解释器及依赖来自账户唯一标准环境；发布物不包含 `pyvenv.cfg`、解释器或 site-packages 副本。启动及回退均校验真实 `sys.prefix`、该版本依赖和代码身份，缺失或不兼容时拒绝，不临时补包。
- 不再使用源码 checkout 中的私有 Python 环境。历史 `.venv` 名称可以是已登记的稳定代码入口，不能仅凭名称判断重复环境；退出旧安装路径仍须单独验证。外层代码发布与 sealed SCL 内层发布保留各自完整性职责，以回执和实际加载证明配对，不把多个指针合并或删除安全检查。
- 发布不携带全量 `.harness` 业务账本、数据库、密钥或运行日志。系统 Python/Node、macOS 框架及共享第三方 Agent Runtime 是声明并验证的外部依赖；PULSE 专属组件和环境由平台管理。不另造系统包管理器，不盲搬整个用户 HOME。
- 安装、部署、回收不得覆盖或递归清理整个 `PULSE_HOME`。程序升级不重建生产库、信任根或工作身份，不用模板覆盖已有业务配置。模块确需数据格式升级时，显式声明兼容范围、备份和升级步骤，不混同为旧根搬迁。
- `secrets/` 统一位置但不共享权限；按实际服务身份限制读取。相同 UID 下分目录不是强安全隔离；不得因迁移撤销其他业务共享凭据。
- OS 服务注册、命令 launcher、macOS 应用入口可位于系统要求的位置，但只能指向已登记的发布物，不在那里隐藏第二份运行数据。Stats 的签名、容器和系统入口适配须实测；与目标布局存在实质冲突时先修订方案，不用永久旧根例外冒充完成。

## 4. 入口、路径和跨模块消费约定

以一份受版本管理的模块/节点部署映射及其受控本机配置为依据，复用已有 registry/manifest，不另建配置服务。模板不含秘密，生产秘密只记录引用。部署、启动、读回与恢复必须消费同一份有效映射；禁止每个脚本重新猜目录。

实施清单每行至少包含：**节点/角色、运行身份、模块和服务/CLI/cron/GUI 入口、程序发布路径、业务 cwd、配置/数据/信任材料源→目标绝对路径、写入者和消费者、必要环境变量、外部依赖、启动方式、验证和恢复方式、旧入口退出条件。** Linux 两节点、ownermac 和 Actions 分别登记；Actions 是构建/控制执行面，不是假定拥有一份生产业务库的第四节点。

生产入口必须从已登记配置得到目标根与必要路径，不能上溯代码目录、依赖当前 shell 的 cwd/PATH，或静默退回旧根。显式参数不得越过登记的生产目标；开发模式可以有独立默认值，但不能自动回退进入生产或反向使用生产数据。配置、数据或信任材料缺失时明确失败；首次空实例初始化与已有实例升级/灾备恢复分开，不能把未挂载的数据盘当作新实例。

| 已知消费者关系（源码线索，不是当前部署证明） | 实施必须消除的歧义 |
| --- | --- |
| [Relay config-paths](../Relay/src/config-paths.ts) 从代码位置推导仓根、配置、metering 和部分业务写域 | 新 release 布局下显式解析生产路径；程序根不能变成业务 cwd 或扩大 Agent 写权限 |
| [Relay Harness client](../Relay/src/harness-continuation.ts) 保存 executable 并在后续命令中调用 | 按第 5 节固定进程使用的 Harness 版本，不能在一次服务生命周期中暗换组合 |
| [Stats](../Stats/README.md) 的固定远端 exporter 与 ComputeCost shadow 路径 | 客户端、远端 exporter、计量生产者使用同一部署映射；只搬服务端目录不算完成 |
| [Platform](../Platform/README.md) 写 Relay 配置及租户工作区 | 本轮排除，不盘点、迁移或验收；不得借 Relay 维护改变其配置或租户范围 |
| [ComputeCost](../ComputeCost/README.md) 消费 Harness、Relay、Pi 与 Codex 输入 | 区分平台专属持久状态、业务工作区和外部共享运行环境；迁移后归因、游标及恢复输入仍连续 |

两份主机配置可以有不同绝对路径，但同一主机的每个持久对象只能有明确的活动位置和写入归属。允许暂存/备份，不允许不登记的旧路径 fallback。

## 5. 长期自动构建与部署合同

本节是**必须实现并持续维护的能力**，不是本 PR 已提供的命令。可由现有脚本组合实现，不要求引入部署服务、编排平台或另一套授权协议。

### 5.1 复用现有入口，明确更新触发

优先迭代 [pulse-release-writer.py](../Scripts/pulse-release-writer.py)、现有 [deploy.yml](../.github/workflows/deploy.yml)、[deploy-tcloud-relay.yml](../.github/workflows/deploy-tcloud-relay.yml)、[deploy-bigbird-relay.yml](../.github/workflows/deploy-bigbird-relay.yml) 和模块构建/安装入口，将可复用逻辑下沉至仓库脚本；Actions 只编排、传递已验证输入并收集结果。现有入口以 Relay 为主，**不宣称已满足全模块合同**。收敛后同一节点/模块只能有一个活动部署写入路径，旧 wrapper 只可委托该入口或退役，不能长期双写。

正常链路为：

```text
PULSE 默认分支更新 → 同一 SHA 的适用 CI 成功
→ 计算每节点受影响模块/依赖与允许发布范围
→ 构建及校验 → 安装候选 → 切换/必要重启
→ 实际版本与业务入口验证 → GitHub 记录逐节点结果
```

首次迁移另批维护窗口；启用持续部署时明确批准节点、模块和兼容更新范围，保存为受控配置。**启用后，范围内的正常更新自动推进，不要求用户每次手动编译、复制、接线或重新输入部署确认。** 未启用前本 PR 不改变现有生产行为。增加目标、变更权限/信任根、破坏性数据升级、整机重启或超出已批准维护影响的操作仍需专项批准；不能通过自动化扩大授权。

保留受控的手工重试、只准备不切换和程序回退入口，但它们使用相同脚本和校验；只准备不能报告已部署。生产只接受经过验证的确切 PULSE 提交，不在执行中漂移到新的 main。GitHub PR/Actions 是正式控制面；构建优先 Linux runner，确需 macOS/本机能力时走 Actions → ownermac；SSH 仅作受控节点执行通道。未审 PR 不能获得生产写权或通过特权 workflow 执行任意脚本。

### 5.2 更新选择与可重建发布物

- 将待发布 SHA 与**每个节点上次成功部署记录**比较，识别源码、依赖锁、构建/启动脚本、配置模板和执行策略变化；不能只比较最新一次 push，否则会漏掉离线或失败期间的更新。模块删除/改名也是变更，必须明确处理，不静默遗留旧程序。
- 纯文档或纯协作事实变化不重装程序；同目录内的策略/脚本不能整体豁免。为实际模块维护小型显式依赖表；变更影响到哪些消费者、需要重建还是只需兼容验证/重启，分别列明。未知影响停止自动切换，不猜测无关。
- 使用固定源码、已锁定或明确版本化的依赖及目标 OS/架构工具链自动编译/打包。缓存只复用匹配源码输入、锁文件、工具链和平台摘要的产物；不从开发 checkout 捡取未核实的 dist/venv，也不把 macOS 原生产物拷到 Linux 冒充同一构建。
- 每个候选有不可变 manifest：目标提交、模块来源/内容摘要、依赖与工具链、平台、跨模块和数据格式兼容范围。未变模块可复用已验证产物，不强迫无关模块重建；新集合必须完整描述实际组合，不能把复用旧模块伪报为新源码重建。
- 发布不得引用 runner 临时目录、CWA 旧 Harness 安装或可变源码树。代码入口、标准 Python prefix、原生依赖和 app 资源按实际最终路径验证；构建复用标准环境，离线且不建立构建隔离环境。改变稳定入口须验证原安装历史与回退绑定，不能用复制 venv、改 YAML 或手换软链接冒充受管接管。候选准备不等于激活，失败候选不可被 current 选中。

### 5.3 安装、切换、重启与失败处理

部署脚本至少完成以下步骤；不要求为步骤发明新协议：

1. **预检**：核对 GitHub 来源/SHA/CI、节点身份与角色、有效映射、目标路径、容量、服务身份权限、外部依赖及现有数据/信任材料。持久目录和候选不得通过软链接或错误变量别名互相覆盖。获取同节点共同的部署互斥，普通部署、回退、回收及一次性维护不能并发争用目标。
2. **准备**：自动构建并检查候选、依赖和配置；需备份时验证恢复对象完整。准备失败不改活动程序/启动配置，不停健康旧服务。候选或同发布标识已存在时校验内容，不覆盖不可变发布物。
3. **切换**：在有界窗口内排空受影响任务或按现有生命周期安全暂停，不能为重启直接杀掉未结 WI/消息并假定未发生。按依赖顺序切必要的服务与调用方；超时先读回并保留可恢复状态。不涉及的模块无需重启。
4. **持久启动**：自动安装或更新实际 systemd/launchd/launcher/app 入口的受管部分及其配置引用，reload 必要的服务定义并重启受影响组件；不依赖交互 shell 的 export、当前 ssh 会话或 runner 的 PATH。启动配置必须能在部署进程退出后独立工作。
5. **验真**：自动读回服务注册、PID/启动时间（适用时）、实际程序和依赖版本、有效路径及配置引用，并执行模块业务 smoke。进程存在、端口打开、指针已切或脚本退出 0 均不单独构成成功。失败时输出非零结果、失败阶段、实际版本和下一恢复动作；不得发布成功回执。

部署至少保留操作目标、原版本、已完成步骤和真实读回的小量持久记录，且在不可逆动作前记录意图；记录不得包含秘密或消息正文。相同候选重跑先校验活动状态，健康且一致时不重复重启、不重放业务动作。中断后重跑先查实际服务、指针和记录，不能盲目从头复制、重发或覆盖较新的部署。复用现有锁与记录能力，不建立常驻自动续跑服务。

失败候选尚未接收新事实且数据兼容时，可由相同脚本恢复已验证旧程序与启动配置并重新验证，保留“部署失败、已恢复”的结果；新端已写数据或外部效果未知时遵循第 7 节，禁止回放旧备份伪造成功。自动任务不能无限重启重试。

### 5.4 current、进程版本和发布物回收

`current` 是所选发布集合，不天然证明每个在运行进程已采用它。启动包装在一次进程启动时解析集合，固定实际程序及必要跨模块 executable 的不可变路径；之后不能因 current 改变，让旧 Relay 暗中调用另一个 Harness。确需动态解析的调用必须声明并测试兼容范围，否则重启受影响调用方。

未变模块可继续运行旧集合中内容等价、兼容性已验证的产物；部署结果分别记录目标集合与各模块实际路径/摘要，不强迫仅因目录名变化重启全平台。机器或服务下次启动必须按持久启动配置恢复所选有效组合，而不是回到旧源码入口。

回收是部署脚本的显式动作，先读取活动进程、在途任务、恢复记录及回退保留要求。只保留 current/previous 不够；被仍在运行的旧进程或恢复流程引用的发布物必须保留。无法证实无引用时不删除；容量不足应停止准备而不是冒险清理数据。

### 5.5 重启可用与多节点结果

每次部署都要验证受影响服务重启后的真实入口。首次能力验收还要在批准窗口内，验证实际目标节点整机重启后的恢复：Linux 常驻服务按已登记的 system/user service 策略自动启动，用户服务的会话/linger 等前提明确验证；macOS 按对应 launchd 与登录条件恢复。GUI 不伪装成可在无人登录时工作的 daemon；Stats 按登记的自动启动或按需启动方式验证原应用入口，无需重新安装、编译或手工补环境。日常部署不为证明这一点擅自重启整机。

每节点按角色只安装需要的模块，跨节点版本过渡必须符合已验证兼容组合。自动发布采用已登记的顺序，节点失败/离线后停止依赖它的后续切换并记录未完成范围，不把其他节点成功汇总成全平台成功。恢复节点从其实际已部署基线重算差异；过期的排队任务不能把更新版本覆盖回旧版本。非兼容变更在维护窗口内协调切换，不声称多机原子发布。

## 6. 一次性迁移实施顺序

已完成的源码导入和账本读者采用不重放。剩余对象逐项以实施清单和隔离验证决定最小变更；生产维护另行核对精确授权。一次性迁移复用第 5 节的长期部署能力，不生成只在本次有效的启动方式。

1. **刷新一张清单**：按第 4 节逐节点枚举实际程序、数据、信任材料、业务现场和全部消费者；查证备份、容量、在途工作及恢复位置。历史盘点不是当前健康证明；过期状态按 unknown 处理，由实施者取证，不让用户代收日志。
2. **准备单仓与持续部署候选**：源码/历史及账本冲突处理分开审核；将必需依赖纳入 PULSE，迭代既有构建/部署脚本和节点映射。候选不具生产写权；不重写 Harness，不新增通用迁移授权或执行框架。
3. **先验证最难的接管，再验证部署循环**：在安全隔离副本验证旧路径授权、Host 信任、Git worktree/common-dir 与原 WI 连续性；无法安全隔离真实副本时先去敏/解除外部写通道，不运行带生产写权的副本。接管可行后，用同一部署入口完成安装、后续模块更新、重复执行、服务重启和失败恢复。实测容量和耗时后才确定维护上限。
4. **获准后维护**：暂停受影响旧写入、调度及自动重启，核对在途效果并固定 Git 账本切点；数据库及附件取得一致备份后复制到目标，保留原件。不热拷贝单个 SQLite 主文件，不用 mv/clean 搬 WI 工作现场。
5. **核验后切换**：经受支持的配置、安装和接管流程绑定目标，由长期部署脚本安装候选与持久服务入口，逐项读回；关闭旧 Harness 发布路径，确认 CWA 其他业务不受影响。局部文件指针可原子替换，多服务多节点不是一笔原子事务。
6. **验收并交接日常更新**：完成第 8 节的真实业务、重启、升级及恢复验收；按批准范围启用常规自动发布。独立审核后按清单退役旧入口，稳定后再单独确认原件清理；长期部署脚本、Actions、模板、测试及恢复记录保留维护。

迁移中断即停，先确认已发生事实再决定继续；未知外部结果先读回，不能按“未执行”重发。维护停写使用现有服务管理与访问控制，不另建全局平台开关。

**不能人工绕过的停止条件：**

- 旧授权、sealed 包装、注册及工作树仍可能绑定绝对路径。Git 外统一根没有自动解决这些绑定。优先验证现有正式接管能力；不改签名、手改数据库或伪造 reinit。不支持时提交最小适配审核，保持旧系统服务，不先停机再补实现。
- 凭据权限、macOS 容器/签名与数据库兼容性未经隔离验证，不放行。不声称全部目录可仅靠复制与配置变更完成。
- 旧服务、调度、自动重启、publisher/reconciler 或其他实际入口仍可能恢复旧活动写入，不放行。关闭实际旧写通道并验证 CWA 非 Harness 业务，不能借机恢复旧提案的通用隔离平台。

过渡期间可由旧根维持原服务，但须列明消费者、负责人及退出条件；不能永久保留每模块各自的旧根，也不能用旧路径 alias 冒充完成。

## 7. 程序回退、数据连续性与灾备

| 情况 | 处理 |
| --- | --- |
| 新端尚无新事实、尚未切权 | 核对两侧实际状态后恢复旧服务/启动配置，保留候选与诊断；超时不等于未切换 |
| 部分服务已切换 | 暂停受影响写入，逐项读回，恢复受支持组合；不盲切总指针，不让两端同时写 |
| 新端已有消息、checkpoint、授权、计量记录或外部效果 | 保全最新数据，优先换兼容程序；不能恢复旧备份抹掉新事实或重放已生效动作 |
| 数据格式已升级 | 仅经验证能读当前数据的程序可回退；previous 存在不是兼容证明，不自动反向改库 |
| 灾难恢复 | 恢复数据、附件、信任材料、配置及对应程序组合，由长期部署入口恢复服务；Git clone 不是完整备份，须有独立故障域副本并验证恢复 |

旧 OS 文件锁/PID 不作为活进程恢复；持久事务、逻辑 lease 和待处理队列不得一律清空。回退不重建密钥、不重置工作身份；灾备未完成时不能先启动一个空库服务。备份/恢复过程中禁止两个副本同时作为活动写入者。

## 8. 完成标准与证据

本 PR 请求复核的是单仓归属、统一布局、**长期部署责任**、一次性迁移顺序及停止条件；不是生产切换许可。实施验收必须绑定确切源码/产物、节点、有效配置摘要、时间和真实读回，证据回到 GitHub PR/Actions，敏感内容不进日志。原审查不自动覆盖后续提交。

| 验收 | 必须举证的结果 |
| --- | --- |
| 单仓与路径闭合 | 只取 PULSE 和声明外部依赖即可构建/安装/恢复；旧 CWA Harness 安装不可用仍能工作。程序、业务 cwd、配置、数据、秘密、备份与所有消费者均可定位，无旧根 fallback |
| 首次安装与后续更新 | 在适用 OS/架构上，由同一长期入口自动完成 R1 安装与 R2 模块更新；证明编译产物实际加载到目标节点，而不是源码已拉取或文件已复制 |
| 变更选择 | 纯账本/文档不重装；源码/依赖/执行策略变化正确触发；依赖消费者被纳入；节点漏过一次发布后仍能补齐差异。未知影响不误判无变更 |
| 重复、并发与中断 | 相同健康版本重跑不重复重启/副作用；部署、回退、回收互斥；准备/切换/重启后中断再执行能先读回，不覆盖更新版本或抹掉在途事实 |
| 服务与整机重启 | 每次受影响服务重启后业务可用；首次验收另有批准后的整机重启/登录恢复证据。无需手工 export、cd、改配置、重建 venv 或重新编译 |
| current 与回收 | 旧进程不暗换跨模块 executable；目标集合与实际运行摘要可核对；仍被进程/任务/恢复引用的旧发布目录不会被回收 |
| 失败与数据保全 | 构建失败、缺配置/权限/空间、缺或损坏数据挂载、重启/健康检查失败均不报成功。验证兼容程序回退与真实备份恢复；新事实不丢、信任身份不变，不创建空库掩盖故障 |
| 本轮适用业务 | 原 WI 接续与适用 checkpoint/rollover/恢复、Relay 收发与重启恢复、Stats 来源/时效和 ComputeCost 连续读取分别举证。继承适用的既有结果，不重复用户已确认的基本通信 UAT；Platform 排除，Stats/ComputeCost 业务修复不转入本轮。使用受控 canary，不制造无关副作用 |
| 多节点与旧权威退出 | 所有活动节点完成或明确停止/退役；部分失败、离线、版本不兼容如实报告。旧写入端重启不能恢复第二权威，CWA 非 Harness 业务保持可用 |
| 日常部署交付 | 脚本、模块/节点映射、服务模板、CI/Actions 和操作/恢复说明进入 PULSE；批准范围内自动触发，并有实际 GitHub run 证明。人工搬运成功不能替代自动部署验收 |

使用现有测试框架补齐正常、失败、回归、回退、并发/幂等和隐私安全测试；真实 macOS/resident Linux、默认分支复验和适用 smoke 不能仅用 mock 或历史 CI 替代。任何未验证项写明未完成，不以平台其他模块成功补齐。收口清理临时工作树/工作流时，只删除明确的一次性材料，不删除长期部署能力。

文档修订、隔离验证、生产采用和正式结算分别报告。实现中的实质差异须回到方案审核；实施前通过原 WI/checkpoint 关联目标、验收项与版本。不手改历史签名、回执或生产状态制造同步成功，也不把其它 WI 的 Outcome 或人类豁免转用为本 WI 验收。
