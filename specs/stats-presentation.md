# Stats 呈现：信息分层与统一阅读网格

状态：现行五卡片、双入口明细与双行菜单已部署；2026-09-19用户确认基本符合预期。采用及验证统一见[已证基线](stats-query-dashboard.md#已证基线与边界)。
范围：仪表盘、要你出手、在办、自动任务、产出与成本，以及标题和页脚。
沿用 WI300 的只读来源；不改变 ComputeCost 计价、SCL 权限、业务 cron 开关和退役事实。

## 布局

面板仍为 420×580 点，外边距14。五个卡片均为392点宽、内边距10、圆角10，
中性标题与相同留白。颜色表达具体状态，不把标题、年龄或普通库存一律染成告警。
Oikos 位置保持总览下方、WI 账本核验上方。已批准的“待恢复”仍是明确暂停。

统一折叠控件：全行可点、键盘可操作、明确展开/收起状态；详情全文左对齐，
保持相同缩进。初始收起；刷新不打断主动展开。数据说明收进页脚入口，不常驻
生产者名、能力建设计数与版本。缺失/过期等重要限制仍在受影响区显式显示。

## 平台运行 · 当前

此读数只回答最新有效观测下平台是否运行正常，不再判断整天/周/月的历史覆盖。
今日/周/月仅影响新增 WI、PR 数、总成本和下方明细；已恢复历史事故不把当前染红，
WI 账本核验保持在独立核验区。面板标题保留状态灯和快照更新时间；运行异常时附运行状态，
无待办且运行正常时附“正常”，不写待办数；待办数由菜单栏 WI badge 和“要你出手”卡显示。监测覆盖不进标题，留在“数据与覆盖”说明。运行/资源关键读数缺失、未来或过期不能显示正常。

## 产出与成本

“产出”列是该行 WI 本期由内核合并的 PR 个数，写“N 个 PR”：确证没有写“0 个 PR”，内核记录未取到或该 WI 读不到写“未提供”，非 WI 写“—”；同一 WI 多行显示同一数字，跨行不可相加。
口径见[ComputeCost 需求](pulse-compute-cost-requirements.md#wi-产出内核合并的-pr)。行详情先列“产出：合并 PR N 个”、该 WI 本期金额与每 PR 成本（只有已计价部分时写明）、
每个 PR 的仓库与号、审核分数与轮数、合并时间；其后“验收成果”照旧列原生 WI 成果，两者并列。
表格下方一行显示近 7 天 PR 产出异常：“未经内核合并 N 个 · 直接提交 main M 个”，有异常为橙色，可展开逐条查看；
未设强制生效日时不写“未经内核合并”，没有内核记录的 GitHub 合并另起一行灰字“近 7 天 GitHub 直接合并 N 个（关卡尚未强制）”，生效日前的同样只作参考；
GitHub 未读到、读取过期或内核记录未读全时写“未核验”及原因，不写 0。统计详情另列本期“合并 PR（内核）”合计。
其下按所选期间再起一行灰字“本周另有 N 个已合并 PR 未经内核登记 · 分支前缀提示（未核实）：hestia 10 · duke 3 · 无提示 2”，可展开逐条看仓库、号、分支和提示 Agent；
提示 Agent 取分支名 `<agent>/` 前缀，且须是团队登记表中的 Agent，否则计“无提示”；这些 PR 不计入产出、每 PR 成本与 Agent 归属。N 为 0 时不显示；未核验时写原因（含“GitHub 读取未覆盖本期起点”），异常一行已写未核验时不重复。
子 WI 单独成行，WI 栏写“↳ wi_…”，行详情写“子 WI · 父 WI：<编号 名称>；本行只计本子 WI”；有子 WI 的父 WI 行详情另写“含子 WI 合计（本 WI 与 N 个子 WI）：金额 · M 个 PR”，取发布物 `work_item_families`，父 WI 本行金额、产出与表格总计不变。主会话经 `review_child` 通过的子 WI 成果显示“主会话审核通过（非人类验收）”。
主弹窗改为Agent/WI/产出/金额四栏轻量清单，最多显示同一查询筛选后的前5行，
显式显示数/总数；表头与内容随主面板滚动，不浮动、不内嵌第二个纵向滚动容器。
查看全部打开唯一、可调大小的明细窗口，保留八列、列宽、筛选、排序与行展开。
两处共享同一App SnapshotStore和期间/筛选/排序/选择，打开窗口不触发新取数或重算。
完整窗口有独立的列宽偏好，首次采用宽窗默认宽度，不把窄窗遗留超宽列塞回新窗口；
旧偏好原值保留不删除，新窗口的用户调宽照常保存。
完整表的表头在scroll之外的独立同级viewport，原生列头仍负责调宽/排序；仅水平位移与
表体同步。表头与表体有独立矩形和裁剪边界，原生contentView显式clipsToBounds，
不能仅给整个scroll圆角遮罩而允许行绘制越过表体。无外层滚动再套完整表。
刷新使用同一发布物；过期按下文“保留上次数据”显示，不兼容不显示内容，不维持假正常。
所有列使用原生 cell 容器，文字统一按行中线垂直居中，复用和列宽改变后仍成立。
文字列左对齐，数量/金额列右对齐，表头方向一致。弱化边框，只留轻水平分隔线，
一条明细对应一个选择高亮；筛选与刷新不能让高亮和展开对象不同。
有溢出时保留原生滚动条，无溢出时隐藏空滚动条，不把横向列隐藏为不可发现。
已知零与未知分开；正数不足1美分显示 `<$0.01`，精确值仍在明细，不假装免费。
原始用量数量、截止时间、完整覆盖和技术凭据收进既有“统计详情”；不删原内容。
未知来源不能因没有 error 字段就写“已读取”；采购请求数缺失也不补0。
完整明细的部分计价汇总必须就地标明“已计价部分”和“完整成本未知”，包括部分金额为零时；不得仅以“总计 $0.00”替代未知的完整成本。
点击平台状态打开 Oikos，不再错误地打开成本凭据。

## 保留上次数据

新数据算好后再替换，旧数据一直显示到被替换；任何时候不因刷新中、刷新失败或过期而空白（大鸟 2026-11-04）。

- 成本发布物过期、跨北京时间日界、刷新中或上次刷新失败时，仪表盘“PR 数／总成本”、产出与成本卡、完整明细窗口与行详情继续显示最近一次有效发布物的全部内容。
- 卡片与明细窗口顶部橙字写“数据截至 HH:MM（已过期 N 分钟｜刷新中｜上次刷新失败：原因）”，只列成立的部分；跨日界时前加“以下为 M 月 D 日数据”。仪表盘两格数值灰显，副标题改为“截至 HH:MM”；卡片内容降低不透明度。
- “刷新中／上次刷新失败”取发布器周期状态 `cost_refresh`，只说晚于所示数据的周期；原因只显示固定中文短语，不显示异常原文。
- “今日已记录用量”只取同一北京日期的发布物；跨日界后显示未更新，不把昨天称为今天。
- 只有手头没有任何可显示的发布物时才不显示内容并写原因：从未有过数据，或仅有格式不兼容、时间异常（生成时间晚于现在，或有效期不在 0–75 分钟内）、无金额（`unavailable`）的发布物。
- 新取到的快照若缺成本、不兼容或无金额，不替换已显示的有效数据；只有生成时间不早于它的有效发布物才替换。

## 卡片顺序

仪表盘之后依次为：产出与成本 → 在办 → 要你出手 → 自动任务。要你出手只放需要大鸟本人
决定的事；在办是各 Agent 的工作看板；自动任务只放登记的定时服务。

## 要你出手

WI卡片默认主标题为 `Pulse · wi_20260906_779`，辅助行保留原事项标题；
原请求全文和其它状态展开查看。状态/创建时长标签如 `in_progress · 10 天`。
年龄色阶为0–7天绿、8–30天橙、31天及以上红；时长未知灰色。色阶只表示创建年龄，
不判断故障、实际执行进度或连续停滞。窄面板不足以容纳标题和标签时标签自然另行，
不截断WI编号或状态。默认折叠、原有左对齐不变。

列表按WI原created_at的创建时长从长到短；同天按原时间先后，末尾用WI编号稳定
排序。缺时间的记录保留且排最后，不从updated_at、handoff时间、WI编号推算创建日期。
人工请求通过显式work_item_id关联同一快照中的唯一WI记录，不解析正文或meta反猜
身份；引用缺失、对象缺失或重复时仍显示原请求，不造状态、年龄或负责人。

流程标签和展开详情均显示 SCL 已证明的当前有效 `workflow_profile`。同一 WI 正式
从 lightweight 升级后显示 standard；原始启动事实仍保留在 SCL，不用当前标签重写历史。
仅消费通过四端权威核对的读模型；证明缺失或冲突时省略标签，不从图或检查点推断升级。

## 在办

「在办」替代原「在飞项」卡片和挂在「协作收件箱」下的合同明细。数据来自 exporter 的
`work.board` 指标，由内核 `stats-facts` 的 `items` 与 `collaborations` 生成；App 只排版。

- 范围：全部非终态 WI（草案、进行中、已停、移交中），以及未结合同和 24 小时内结案的
  合同；已撤回的合同不显示。标题写总数，如“WI 17 · 合同 9”。
- 分组：按“下一步该谁动”分到 Agent 名下。合同放在 `next.actors` 的第一位：待接、
  办理中是接收方，已交回、已完成待采用是发起方；没有下一步（如已拒绝）时放发起方。
  WI 放在持有人名下，无持有人放负责人名下。每张合同、每件 WI 恰好出现一次。
- 计数守恒：各组 WI 数之和等于在办 WI 总数，合同数之和等于显示的合同总数。App 发现
  行数与总数不符、行不属于任何 Agent 或编号重复时，整张看板显示“读不到”，不显示成
  “没有在办”。
- Agent 排序：有卡住项的在前，其余按最近动静排，不按字母。只有一件在推进的 WI、
  没有合同的 Agent 合成一行，如“Asobi · Duke · Emi · Ken  WI 各 1 · 均在推进”。
- 折叠行：Agent 名、WI 数和卡住摘要，如“待接合同 4（最久 5 天） · 交回待处理 2”。
  展开后一件一行：合同写方向 + 对方 + 目的首句 + 状态 + 时长；WI 写摘要（无摘要用标题
  首行）+ 最近一次推进距今多久。合同只投递给主身时加“主身”标记；`main_only` 不再作为
  WI 的分类。点开一行才显示合同号、工作项、下一步、时间线或 WI 编号、负责人、时间。
- 卡住（橙色）：合同待接超过 6 小时或过了期限；合同已交回或已完成，发起方还没处理；
  WI 超过 7 天没推进（与停滞列表同一阈值）；草案超过 3 天没推进。
- 与「要你出手」：同一件 WI 已在「要你出手」时，在办只加“已在要你出手”标记，不展开
  第二份原请求。
- 降级：快照过期时写“以下为上次记录，当前状态待核验”；账本跨端一致性未核验时写
  “已读取当前账本，跨端一致性待核验”；合同来源不可用时只列 WI 并写明。
- `harness.wi.in_flight` 仍导出全部非终态 WI，供「要你出手」的 WI 身份标签和 WI 日巡读取。
  界面生成的时刻统一北京；原始计划与引用保留其明确时区。

## 验收

独立快照查看入口复用正常 App 的解码、面板和明细，启动后直接显示独立窗口，并明确标识本地来源；不另占一个容易混淆的菜单栏入口。
只读原始发布物，Refresh 只重读指定文件；无生产传输、持久缓存、历史和表格偏好写入。
缺文件、损坏、过期、未知与正常读取执行相同呈现规则，不以导入时间覆盖原观测时间。
只导出成本时，未读取的平台健康和 WI 权威仍为未知。真实发布物经独立入口的原生呈现与
生产通道验收分别留证，前者不证明生产同步已成功。

正式 native macOS 验证全部八列在不同高度/复用后的垂直中线、前四列可见、单行选择、
过滤恢复、列宽与滚动；实际420点面板明暗两种外观、卡片同网格、默认收起和详情左对齐。
增加连续首/中/末/回到顶部、横拖、调宽、过滤开关、选择与刷新组合；不仅检查静态
文字几何，还逐帧比较表头区域像素，防止表体穿透。验证关闭弹窗/重开明细仍为一个
窗口、共享查询与状态，不额外访问生产来源。
未知、零、微额、过期、空集与仅有成果的情况不得被美化成成功。再通过原安装/两次
自然发布/重启回读核对当前三个 activity 成本视图；旧21视图发布物保留兼容读取验证，不启动暂停的业务来制造成功样本。


## 来源与菜单入口补充

当前来源可靠性与菜单入口遵循[来源可靠性](stats-source-reliability.md)。菜单使用同一个原生模板图像并排绘制三个双行 badge：**CODEX** 和 **CC** 下方各显示 7 天额度已用百分比；**WI** 下方显示“要你出手”当前 producer 计数。三个 badge 直接消费各自事实源，不互相推导。
单个原生模板图像确保菜单栏抽取标签时两行都保留，深浅色由系统处理。CODEX 与 CC 都使用当前 7 天窗口内的最近额度读数（Codex 来自账号查询，CC 来自 Relay 真实回合）；缺失、早于当前窗口或已重置时显示横线，不以 Token 或成本推算。当前 snapshot 存在时，WI 保留与“要你出手”卡片同源的 alert_tiers.act 汇总；部分请求来源待核验时数字仍可读，并以独立 ? 标记表达不完整性。只有没有 snapshot 时 WI 才显示横线。
运行异常、数据待更新或夜间静默继续用独立 ! / ? / ◐ 小标记表达，不以状态标记替换 CODEX 或 WI 的有效数字。Oikos已过期样本可以灰色
历史读数展开，不能给当前平台状态背书；白天沿用原loop在已知资源expiry前读取。


用量来源故障要点名具体来源及影响，如“TCloud用量同步未完成”，点击原地展开；
说明最新成本可能不完整、历史已入账数据保留，不把传输失败说成主机宕机。
周期状态中为 `paused` 的节点在数据源明细写明“TCloud：按决定暂停采集，本期覆盖不含该节点；已入账历史保留”，其来源行显示“按决定暂停采集 · 历史记录保留”，不计入读取故障。

传输容量与历史守恒是后端合同，见[ComputeCost传输设计](pulse-compute-cost-design.md#传输安装与恢复)及[实际恢复记录](evidence/stats-readable-summary-20260918.md)。界面只显示当前证据及影响，不因故障已修而屏蔽后续真实断连，也不因同步成功推断全部历史覆盖。

独立快照与正常来源均须在主面板及完整明细直接显示读取失败；若保留上次数据，应标明这是旧数据。恢复读取成功后清除失败提示。数据格式不兼容与一般读取失败分别表达，不将技术错误内容直接展示给用户。
