# Stats：Oikos 平台概览与自动任务卡片

状态：已实现、已安装并通过暂停态实际消费验证；用户确认全部 cron 因平台迭代而计划暂停，后续逐项启用。
关联：WI300、WI825、PULSE #595；不扩展 ComputeCost 计价或 SCL 执行权。
本设计替代旧“未闭环事故 / 监控待修复”产品方向；首次采用见第11节，当前运行及2026-09-19用户确认见[统一基线](stats-query-dashboard.md#已证基线与边界)。确认暂停态体验不代表重新启用后的自然交付已验收。

## 1. 用户结果

打开原 420×580 点面板，按用途找到任务，不展开就能看出它在哪运行、什么时候做、最近做了没有、
本期状态如何（布局见第 5.1 节）。平台资源按需查看，不把旧探针停用当业务失败。
用途分组首次打开为展开，任务和 Oikos 详情首次打开均收起；用户展开或收起后，普通刷新不打断阅读。

## 2. 布局冻结

保持现有仪表盘四个总览、日期切换、成本表和后续卡片的位置；本轮不重排其它区域。
顺序必须是：

1. 仪表盘标题与今日/本周/本月选择器。
2. 平台运行 / 新增 WI / PR 数 / 总成本的总览行。
3. `▸ Oikos 平台概览`（新增，默认收起）。
4. `▸ WI 账本已核验 / 待核验`。
5. Codex 与 CC 的 7 天额度。
6. “要你出手”与“在办”（在办替代原“在飞项”），规则见 `stats-presentation.md`。
7. `自动任务`（替代原“未闭环事故”）。
8. 产出与成本表。

Oikos 展开后复用现有五个计算节点的磁盘、可用内存、swap、可写性、inode、Runner
实际/预期状态，以及真实异常、处置送达状态、采样时间和有效期。保留原指标与含义，
不另造一份资源统计，不把正常高 swap 或按安排停用的 Runner 判为故障。
折叠标题可附一句“资源正常 / 有资源异常 / 数据待更新”，不常驻五台机器的读数。
Oikos 是当前资源视图；切换本周/月不把此刻健康扩写成历史期间全程健康。

给用户，或直接支撑 S1/S2/S3 的运行复核。没有近期可靠运行证据也保留用户明确需要
的条目，尚未恢复时显示灰色“未运行 · 待恢复”；源不可读仍为橙色待核验。
单项启用后独立转入执行/结果状态，不受其它任务仍暂停影响。不筛掉目录中的暂停任务。

### 3.1 服务映射目录

`Stats/exporter/config/automation-tasks.json`（`pulse_stats_automation_catalog/v2`）是唯一的服务映射，
不是第二份可执行计划：

- `services`：稳定的服务 id、名称、负责人、约定结果和各阶段。阶段写实际任务编号 `job`，可写
  `owner`（缺省取服务负责人）、`label`、`skip`（有据静默的状态文字与需告警的摘要规则）、
  `proven_by` 和 `unproven`（本阶段完成还需要、但没有任何生产者回执的条件）。`retired` 列出已退役的
  任务编号及接替者。
- `families`：按任务 id 规则折叠成一行的同类任务（收件箱巡检、PR 审核派发、合同投递），写明 id 规则、
  展开标签、收入方式（`named`：凡 id 匹配即收入，负责人与 id 前缀不符算冲突；`permitted_own`：只收
  负责人与前缀一致且已许可的任务）和各状态文字。新增同类任务按规则自动归位，不逐个加代码。
- 目录加载前做映射校验，有差异即拒绝并逐条写明：服务或家族 id 重复、同一任务映射到两个服务、
  服务阶段又落入家族规则、`proven_by` 指向本服务外、跳过规则无效。
- 目录摘要随各节点快照上报；读取器与生产者摘要不同即视为版本不一致，该节点来源不计入。改目录须三个节点同版上线。

投影对照实际来源，把差异逐条写进行的 `mapping` 与原因，不改业务开关来整理显示：

- 同一任务在多个节点同时启用（列出节点）、负责人与目录不符（写目录值与节点实际值）：橙色“运行归属冲突”。
- 已退役任务仍在某节点启用：橙色“映射待核对”；已退役任务不再单列为新增任务。
- 目录登记的任务未在任何可读节点配置：写“未在任何节点配置”；全部阶段都未启用时仍按暂停安排显示。
- 已启用但执行登记缺失、未许可或负责人不符：全部阶段如此时显示灰色“未运行 · 未获许可”并写明缺哪条登记，
  部分阶段如此时显示“部分阶段未启用”；Stats 不自动登记。
- 迁移：旧节点停用、新节点启用时按新节点判定本期，旧副本的未核销轮次保留在历史。
- 未归入目录的任务单列时 `mapping` 写“未归入服务目录”。

### 3.2 共享检出跟随 main、协作收件箱巡检与 PR 异构审核派发

九项之后的服务行同样来自服务映射：

- “共享检出跟随 main”：`pulse-four-end-sync`，按通用规则判定；跳过摘要含 blocked/failed 时为橙色“同步受阻（已告警）”。
- “协作收件箱巡检 · N 个 Agent”：所有 `<agent>-collab-inbox` 任务按名称规则合成一行，
  新开的 Agent 收件箱自动归入，不再显示为“新增任务”。N 是可执行的收件箱任务数。
  全部按时显示最近一轮北京时间与“全部按时”；有 Agent 失败（红）或未按时、结果待核验、
  归属冲突（橙）时，折叠行写 Agent 名或个数，展开只列这些 Agent 及其状态；正在执行
  不算未按时。本轮被调度器拦下而未运行的成员（灰）也不算按时：只剩这类成员时整行灰色，写“N 个未运行 · …”。
  未启用的 Agent 单列一行“未启用：…”。节点来源不全时写“来源待核验”。
  多个 Agent 有问题时，原因按各自状态分类计数：只有红色结果称“有失败证据”，其余称“证据待核验”；
  全部同一状态时写该状态及原因，不把配置待核验说成未按时或失败。
- “协作合同投递 · N 个 Agent”：只承载对话的节点上，已许可、owner 与 id 前缀一致的 `<agent>-collab-deliver`
  合成一行，规则同收件箱巡检；投递 gate 无待投合同时按约定跳过。未许可或 id 前缀与 owner 不一致的
  投递任务按下段通用规则单列，未许可的保留“新任务必须显式登记执行许可”。没有这类任务时不出现这一行。
- 协作合同不再挂在这一行下面，统一在“在办”看板显示（见 `stats-presentation.md`）。
- “PR 异构审核派发 · N 个 Agent”：已许可、owner 与 id 前缀一致的 `<agent>-pr-review-codex` /
  `<agent>-pr-review-cc` 合成一行，规则同收件箱巡检；N 是 Agent 数，问题按任务计数，展开写
  “<Agent>（codex / cc）”。派审 gate 跳过（PR_REVIEW_SKIP）算按时；gate 通过或派发成功不称代码
  审核已完成。没有已许可的审核派发任务时不出现这一行。

执行登记自 2026-10-19 起只登记具名任务；旧的交接派发与资源告警条目已在两个节点删除，
卡片不再为非 `job:` 条目生成行。没有服务行的其它任务：已许可的按任务定义的 `name`（缺省为 id）
单列一行，按通用规则判定本轮结果；已启用但未许可的显示灰色“新增任务 · …”“未运行 · 未获许可”，直到登记；调度器因缺许可拦下的轮次（`reasonCode=automatic_paused`）同样是未运行；已停用的不显示，仍有未核销轮次时显示灰色“未运行 · 已停用”并列出历史。两者的历史都写进展开内容，缺许可、撤销许可和停用都不核销此前轮次。

## 4. 明确不进入默认卡片

- 每小时 dispatcher、夜巡中间步骤、重复取数、缓存/日志清理、同步与元监控。
- Duke 投入账日快照、周六主动收扫、Pulse S1 周报早核验：默认不各占一行；有已证
  业务关联时放到对应任务详情，不根据任务名推定必需依赖，也不另算一次交付。
- Hestia 每 30 分钟异常分流：不另起一个“探针”条目；已有事实可进入 Oikos 日检
  的处理详情，不能把一次分流成功冒称资源异常解决。
- 已停用的 Aki 夜巡、Aki 周复盘、Hestia 旧周复盘、Ken/S4 周复盘、Hume/S5 周报、
  Hume 内部机器账、Reeve 旧每日夜巡及一次性历史唤醒：不按“代码还在”自动复活。
- 家居设备开关等家庭自动化不在这张 PULSE 重点协作卡片铺开。

不进入卡片不是删除或停用业务任务；也不把只读 UI 设计当作启用旧 cron 的授权。

## 5. 折叠行与三色

示例为版式说明，不是当前运行结果：

```text

1 项失败 · 4 项待核对 · 1 项执行中 · 6 项未运行
已读 3/3 个节点的任务来源 · 时间均为北京时间
        任务            执行计划   最近结果   本期状态
⌄ 资讯交付                                   4 项 · 2 未运行
  › oracle-node-1        每日       11/16      ● 文档已送达
    每日早报            06:15      06:17
  › ownermac            每周五     —          ● 未运行 · 未获许可
    图解播客：收集      22:00      无结果
```

颜色只表达实际运行结果：没在运行（暂停、待恢复、未获许可、已停用）一律灰色，状态以“未运行 · ”开头；
已定性的长期平台缺口（无回执的说明文字、无生产者回执的 `unproven` 条件、未配结果检查）写进状态与原因，
颜色按其余已证结果判断，不长期占用橙色。
任务名保持普通文字，状态文字用四色；不叠加彩色大卡片、机器路径、技术 job ID、
堆叠次数或默认展开的长错误。颜色必须和文字一起表达，不能仅靠颜色。

| 颜色 | 允许的简短状态 | 语义边界 |
| --- | --- | --- |
| 灰 | 未运行 · 待恢复、未运行 · 未获许可、未运行 · 已停用 | 本轮没有执行；写明依据，不是失败也不是正常 |
| 绿 | 已送达、文档已送达、本轮已核验、部分已核验、已执行 · 未配结果检查、已唤醒、按计划待执行、按约定无需执行 | 本轮按时执行且已证结果通过；已知缺口写在状态与原因里；待执行不表示已经交付，静默须有有效跳过依据 |
| 橙 | 执行中、补跑中、运行端未启用、未接入、结果待核验、本轮结果待核验、投递待核验、未送达、运行归属冲突、映射待核对 | 进行中或证据/配置需关注，不统一称为故障；普通执行中不计异常数量 |
| 红 | 执行失败、执行超时、交付失败、核验失败、已过约定窗口未交付 | 仅限同一定义/轮次的已证失败，或当前有效承诺与完整记录证明漏交付 |

已批准的计划暂停显示明确暂停文字，不从 enabled=false 推定有人批准，也不当事故。
红、进行中、待核验和未运行分别统计；不新增一个把所有非绿状态混算的“事故总数”。
用途内的顺序沿上表与服务目录，刷新不让条目跳位；具体异常从文字可扫读，不新增筛选器。

### 5.1 用途分组、四列与两行

- 旧版读取器没有分组与计划行字段时，全部行显示在“用途待确认”，计划第一行写原表达式、第二行写时区。

## 6. 展开信息

每行点击独立展开，最多先显示以下六组；技术回执再按需下钻：

1. 当前查看的任务周期/轮次、应执行计划及其时区。
2. 负责人、实际执行节点、关联 WI（不存在就明确无，不造 WI）。
3. 触发/执行、产物、投递分别到哪一步；按任务要求显示，不强制所有任务有投递。
4. 失败或待确认的具体原因与已知影响；没有因果证据不归咎于磁盘、模型或 Agent。
5. 已证处理者、下一动作/下一次计划；送达一条告警不等于已接手或正在修复。
6. 最后有效结果、原始发生时间、来源刷新时间和结果/回执引用。

日报产物、业务结果正文和敏感路径不进入默认行；只读跳转，不在 Stats 自动补跑、
改排程、改权限、发通知或进行全量重算。任务失败不自动复制到“要你出手”。

## 7. 状态所需的事实，不新增平行控制面

复用上游 jobId、definitionHash、生效时点、应执行轮次、runId、attempt、原结果
与投递回执。任务目录只负责展示选择/业务分组，不成为第二份可执行计划。
先核对现有运行日志和持久回执的覆盖；仅缺少必要证据时在原生产者补留痕。
定义摘要与调度器同一规范化，由 Coevolution `ssot/toolchain/agent-runtimes.json` 登记的 Node
（调度器自身运行的 Node，`{home}` 取执行账户 passwd home）计算，不搜索 PATH；登记 Node 不可用
时任务保持“配置待核验”，原因写明缺少定义校验依赖，不把定义视为已核验。

预期节点为 ownermac、TCloud 与 oracle-node-1，登记在 exporter 的 `SITE_SOURCES`：ownermac 在读取进程内读，
其余节点经 `refresh.json` `peers` 中该主机已登记的 Stats 身份（前缀须与登记一致）运行其已安装的只读快照。
各节点按自身 Relay 路径图读取调度配置与状态；路径图未声明 `cronState` 时与调度器同规则取 `dataDir/cron-jobs-state.json`。
定义校验读各节点自身 Coevolution 检出中的 `agent-runtimes.json`。

禁用来源、旧定义失败、旧机房副本和上期状态不得套到当前任务轮次。已计划暂停不
计算漏触发。源过期/节点无法读取时保留任务名和橙色待核验，不变成未登记或已停止。
每个节点的运行源缺失不得清空其它节点已知结果，也不能宣布“所有任务正常”：每个阶段都已在可读节点启用的服务
照常判定，展开写明哪个节点来源不可读；其余服务显示橙色“来源待核验”并写明缺失节点，已证失败仍为红色。
程序退出 0 不证明产物/投递/业务验收成功；同一 Agent 的另一任务成功不能清除此项。
本地投递（mode=none）的任务按已配置的结果检查判定：产物检查（`expectArtifact`）读
`artifactVerified`，核验命令（`agent.verify`）读调度器记下的 `verifyStatus`，两者都须来自
同一定义、同一轮的原生结果。全部通过才显示“本轮已核验”；核验命令失败显示红色“核验失败”；
已配置但该轮没有对应回执时显示橙色“结果待核验”，原因写明“已配置…，本轮缺核验回执”，
不以配置存在或程序退出 0 代替；两种检查都未配置才写“尚未配置可验证的业务结果检查”。
同一任务下期成功不自动补齐上期欠交，重试恢复必须对应同一轮的欠交承诺。
资源来源的采样有效期与日/周任务结果有效窗口分别判定，不把周报自然变老当服务故障。

### 7.1 本期状态按完整回执判定

- 本期只看当前定义（`definitionHash`）在当前应执行轮次（`scheduledFor` 不早于最近一个已到的计划时点）的回执。
  上一轮的结果，无论成败，都显示橙色“本轮结果待核验”，原因写明上一轮时间与结果；本轮失败为红色。
- 投递任务（mode≠none）须 `deliveryStatus=sent`；另配了核验命令或产物检查时，还须各自的回执通过，才显示
  “已送达”，原因列出已核验的范围。
- 文档与说明文字同段投递：`captionPath` 的缺失、读取不合法或发送失败由调度器判整段投递失败，`sent` 即含
  说明文字；Telegram 文档的模板说明文字随文档同一消息发送。飞书文档的模板说明文字（`delivery.caption`）
  由调度器另发、失败只记日志、不保存回执，这时文档 `sent` 不证明整段送达，显示绿色“文档已送达”并在原因中注明说明文字无回执。
  读取器只导出说明文字种类（`caption`：file/text），不导出内容。
- 定时唤醒任务（Relay `wake`）不起会话：`reasonCode=wake_delivered` 显示绿色“已唤醒”，办理结果看该 WI 的记录；
  `wake_not_delivered` 显示橙色“未送达”，原因写明是否已提醒负责人。
- 目录为阶段声明的 `unproven` 条件没有任何生产者回执，该阶段在其余回执都通过时显示绿色“部分已核验”（已知缺口写进原因），
  原因写明已核验范围与缺回执的条件。Oikos 日检的核验命令只证明 418 记录入账，“应发通知送达”是独立条件；
  30 分钟分流的静默或另一轮成功都不能核销它。生产者为该条件保存回执后，再从目录去掉这一条。

### 7.2 当前与历史分开

行的 `history` 按任务副本逐条列出不计入本期的问题，`note` 给出条数，`attention` 置真；本期颜色不因历史改变，
历史也不因新一轮成功消失：

- 上期欠交：当前定义下、非本轮的未核销失败轮次（列最近三轮的时间与失败种类）。
- 旧定义未核销：定义切换前的未核销失败轮次。
- 未核销记录不完整：记录不是对象或时间无效，不能确认是否欠交。
- 历史摘要不完整：调度器只保留最近 32 个未核销轮次（`resultHistoryIncomplete`），更早欠交缺原证据。
  收敛任务（`convergent`）的成功轮会重读全部状态并由调度器核销此前欠交，只证明现态，不补证截断前的欠交。
- 迁移前旧节点副本、已退役任务的未核销轮次同样列出并标明来源。只有当前行实际显示为本轮失败（红色）的那条回执
  不重复列入历史；配置待核验、执行中、运行归属冲突、映射待核对、停用、未许可和已退役的副本保留全部未核销轮次。
- 已从调度配置删除的退役任务：读取器按目录 `retired` 只读导出它在调度状态里留下的字段（`retired_state_only`），
  不导出定义；节点来源不可读时写明“已退役任务的历史欠交不可得”，不当作无欠交。
- App 展开只显示 `progress`：服务行、家族折叠行（条目前加 Agent 标签）与单列任务都把历史追加在 `progress`
  的“历史（不计入本期）”之后。

补证与核销只基于原始事实和正式决定，不清空 `unresolvedResults`、不改不可变账本、不放宽 32 条上限、
不直接清标记：

1. 补证：按 runId/scheduledFor 从该节点调度日志（`job finished` 行）、产物原件与投递回执核对该轮实际结果；
   同一轮次在调度器里重跑成功即由调度器按同轮规则核销。
2. 核销：原始证据已不可得或业务上不再补交时，需要负责人对“任务 × 轮次（或截断区间）”的正式决定。
   现有平台没有供 Stats 读取的此类决定入口；设计为负责人 WI 上的一条记录（含任务编号、轮次或区间、
   决定与依据），由内核登记，Stats 只读该记录并把对应历史条目标为“已正式核销”，原始条目保留。
   入口落地前，历史条目保持列出。
