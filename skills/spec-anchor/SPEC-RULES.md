# 写 spec 的规则（阶段二）

> 这份规则不是设计出来的，是从两个真实仓库的漂移图里**读出来**的。
> 每条都注明证据；没有证据支撑的条目一律不写进来。
>
> 证据基座：PULSE Relay（TS/vitest，80 份 spec / 806 条声明）+
> finance-engine（Python/pytest，75 份 / 1207 条），2026-07-25 全量扫描。

---

## 零、先说清楚这份规则治什么

两个仓库的失败模式**正好相反**，但根是同一个：

| | Relay | finance-engine |
|---|---|---|
| 勾选率 | 63%（维护中） | 33%（已弃用） |
| 失败模式 | 勾了但没做（假勾） | 做了但没勾 |

**共同的根：完成与否靠人打勾，而打勾不需要任何证据。**

所以这份规则的核心不是"多写字段"，是：**把"完成"的判据从人打勾换成机器可查。**

---

## 一、强制：每条契约声明必须可锚

### 规则

写下一条声明时，它必须落进三类之一：

| 类 | 要求 | 例 |
|---|---|---|
| **可锚** | 绑一个机器能查的东西 | `` `handleStart()` 返回欢迎文本 `` |
| **可数** | 带具体数值 | `重试上限 = 8` |
| **标 manual** | 显式承认不可自动验，**并写观察步骤** | `每进程约 250MB（用 top 看 RSS 十分钟）` |

不许出现第四类：**既没锚点、又没数值、也没标 manual 的裸断言**。

### 证据

两仓合计 2013 条声明，扫描后：

| 形态 | Relay | finance-engine |
|---|---|---|
| 锚点覆盖率（工具能绑上的） | 79.3% | 12.3% |
| 未绑锚点 | 167 | 1058 |

未绑的部分里，**大多数不是内容不可锚，是写法没到位**——这条是本次最反直觉的发现，见规则二。

---

## 二、强制：提到代码就加反引号

### 规则

声明里凡是提到函数、类、字段、配置项、文件，**一律用反引号包起来**。

```markdown
✗  send 时启动 busyCheckTimer（setInterval）
✓  send 时启动 `busyCheckTimer`（`setInterval`）

✗  调用 calculateCost 计算费用
✓  调用 `calculateCost()` 计算费用
```

### 证据（这条最值钱）

我一开始按"有没有代码符号"给声明分类，得出 **60% 是散文、绑不上**。
抽样一看，那些"散文"里全是真符号——`handleStart`、`listIds`、`calculateCost`、
`handleYolo`、`buildRuntimePhotoMessage`——逐个 grep，**在代码里全都真实存在**。

它们绑不上的唯一原因：**写的人没加反引号**。

补上裸符号识别后，Relay 锚点覆盖率从 **48.3% → 79.3%**，且新增的 35 个漂移符号
逐条回源复核，**零误报**。

所以"六成是不可锚的散文"是伪结论。真相是：**六成是可锚内容的不规范写法。**
一个反引号的成本，换回三成覆盖率。

---

## 三、强制：完成的证据是锚点跑得过，不是框打了勾

### 规则

- `[x]` **不作为完成的判据**，只作为人的备忘
- 一条任务算完成，当且仅当它绑的锚点 `holds`
- 头部 `status: verified` 必须与锚点状态一致，不一致就是矛盾，工具会报

### 证据

勾选框在两个仓库**从相反方向失效**：

- **Relay 假勾**：`session-management/tasks.md:46` 标
  `- [x] Unit Test-002：pool.getStatus() 返回条目包含 sessionId（已覆盖，确认）`。
  该测试真实存在、真的通过——但它断言的 6 个字段无一是 `sessionId`，
  且 `ProcessStatusInfo` **全部历史版本从未有过该字段**。是编造，不是过期。

- **finance-engine 弃用**：`income-manager/tasks.md` 头部 `status: "verified"`，
  正文 94 个框只勾 1 个。而 `ProfitSummary` 已实现、`calculate_revenue` 有 3 个测试。
  **活干完了，框没人勾。**

一个虚标、一个漏标，**同一个结论：打勾这个动作不承载信息。**

---

## 四、强制：声明"已接入"要绑 wire 锚点

### 规则

凡是声称"已接入 / 已启用 / 已生效"的，绑 `wire` 锚点，让工具查生产代码里有没有真实调用点。

```markdown
`@anchor wire checkBalance :: wired`
```

### 证据

`metering.checkBalance` 在 `src/metering.ts` 有接口声明、有实现、有 5 条测试，
**生产代码零调用点**——唯一调用在测试里。`onLowBalance` 零订阅者，
而对照组 `onSoftQuotaWarning` 有 2 个真实订阅者。

spec 却把对应任务标为 ✅ 完成。

**"写了函数"和"接上了"是两件事，测试只能证前者。**

---

## 五、强制：数值必须写进声明

### 规则

超时、重试次数、阈值、限额——写下数值本身，别写"合理的超时时间"。

### 证据

漂移形态排行：**烂的是值，不是名**。实测失真幅度：

| 项 | spec 说 | 代码实际 |
|---|---|---|
| busyTimeout | 10 min | 30 min |
| job timeout | 300 s | 3600 s（12×） |
| acceptTimeout | 15 s | 300 s（20×） |
| `maxRateLimitRetriesPerMessage` | 2 | 死配置，真实上限硬编码 `RATE_LIMIT_MAX_RETRY = 8` |

函数名、字段名、env var 名大多存活；**值全在漂**。只绑名字抓不到主要漂移。

---

## 六、禁止：不许写纯形容词

### 规则

删掉这类声明，或改写成可验的：

```markdown
✗  配置校验和错误提示完善
✗  用户操作手册完整
✗  代码风格统一
✓  `validateConfig()` 对缺失字段抛 `ConfigError` 并指出字段名
```

### 证据

纯形容词类占比：Relay 3.7%（30/806）、finance-engine **8.5%**（103/1207）。
这类声明**永远无法判定真假**——写了等于没写，还占据"已覆盖"的名额制造虚假安全感。

---

## 七、按风险裁剪：不是所有 spec 都要三件套

### 规则

| 风险 | 要什么 |
|---|---|
| tiny | 一句话说清改了什么，不必立 spec |
| normal | requirements（含验收）+ 锚点 |
| high-risk | 三件套 + 真实入口 UAT + 回滚路径 |

### 证据

早期版对 22 个功能一刀切用同一套三件套，结果是**薄档**：
`执行顺序` 章节 19 份里只有 7 份写，最薄的 42 字符，且**零下游引用**——真僵尸字段。

字段消费证据（commit + 源码引用次数）：

| 符号 | commit 引用 | 源码引用 | 判决 |
|---|---|---|---|
| 任务 ID `P0-00x` | 144 | 64 | **强制保留**（全库最高频） |
| `FR-` | 43 | 3 | 保留 |
| `AC-` | 24 | 0 | 保留但须补人类验收步骤 |
| `REQ-` | **0** | 1 | **删**（设计的追溯主键，从没人用） |
| L1 roadmap | 全库仅 3 次引用 | — | **删或降级**（对比 architecture 75 次） |

## 八、外行可验收（缺口，未做）

### 规则（待验证）

面向不懂代码的使用者时，每条 P0 验收标准额外要求：

1. **人类操作步骤**：点哪里、输什么、屏幕上该出现什么
2. **可观察的外部现象**（外行没有日志和测试框架）
3. **一句话"没做到会怎样"**，让他判断"是不是我要的"

把 `restartCount 不递增` 翻译成 `连续对话 20 轮不该看到"会话已重启"提示`。

### 证据

143 条验收标准中 **132 条（92%）的验证方式是自动化测试**，仅 7 条手动。
22 个功能**只有 1 份 UAT 记录**，且其中人工验证表 B1–B4 的时间/结果/操作者**全是空的**。

现有 spec 里唯一外行看得懂的是用户故事：

> 「作为租户用户（不知晓自己的 Linux 密码）／我希望发送 `/cc` 后收到可点击链接，
> 浏览器打开即进入终端／以便无需 SSH」

**这条规则我标为"待验证"**：它是从缺口反推的，还没有任何真实外行用过。
不能和前七条（有两仓实测支撑）等同看待。

## 落地方式

规则不靠自觉，靠工具：

```bash
python3 src/scan.py --repo <仓库> --spec-glob 'specs/**/*.md'
```

看两个数，别只看一个：

- **漂移数** — 已绑锚点里断了多少
- **未绑锚点数** — 更重要。一份零锚点的 spec 漂移永远是 0，
  只看漂移会让最烂的 spec 显示为 100% 健康

## 规则九：散文里的数字必须现算，分档必须守恒（2026-08-09，Duke R029 两轮打回沉淀）

锚点有闸兜底，**散文里的总量声明没有**——它是 spec 里唯一没有机器保护的断言类。

1. **总量声明必须现算**：写「共 N 个模块 / N 份文档 / N 条」前，先跑出这个数
   （命令随文附上或指向可复算口径），不许从记忆或上一稿沿用。写数不写口径
   等于把自己置于「两人独立复算撞出同一个数、我成了算错的那个」的位置。
2. **分档之和必须等于实测总数**：把一个总体拆档呈现（正文/附件、保留/退役）时，
   各档数字必须由同一份机检输出按子集复算，且和恒等于总数。拆分数字对不上
   总数的表，比没有表更误导——它会连带把分类判错。
3. **勘误必须扫同源近邻**：修一处计数错时，grep 同一个错误值在同批产出的全部
   出现点（memo/spec/commit message 引块），只修被点名那处等于把勘误句和
   被勘误句并排留在盘上。
