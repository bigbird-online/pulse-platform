# 新内核接入唯一生产账本

生产接入与跨库迁移是不同操作。下述按 WI 接纳是保全历史的过渡机制，不是永久双写者
分区；[整体替代合同](rewrite-pulse-integration.md)规定旧写者清单、退出门及难点承接顺序。
完成替代时新旧 WI 的所有业务决定均由新核心接纳，旧格式只可作为历史来源或投影。
Muse 验证的是新 SCL 的实际执行入口；
不能以旧 SCL 回退、隔离账本试验或源码测试代替生产接入验收。

## 事实与身份

- 既有生产仓库的正式账本及其发布引用是唯一业务事实入口。所有 Agent
  共用同一 ledger 身份；Host、本地缓存和软件版本不能产生另一业务 namespace。
- 原 WI 的身份、定义、全部历史字段、原始事件、已有决定和成果保留。
  未知扩展字段不得因新模型未声明而消失；已结束的 WI 不重新激活。
- 新内核直接接纳并发布同一账本上的新决定。SQLite 可以作为事务内的
  重放和计算工具，但不能在生产接入模式下形成独立提交的第二权威。
- 账本更新必须携带固定来源版本，并在唯一发布引用上原子比较后提交。
  并发变化必须重新读取；远端提交结果未知时只能读回原请求。
  未确认发布的决定不得授权执行或发送外部动作。
- 一个仓库不等于一个权威：未接纳的历史 WI 以原历史文档为基线；第一次接纳将原件与新决定原子纳入日志。此后原件和日志是该 WI 唯一权威，旧 YAML、登记和本地 views 均为输出。删除或篡改投影不得改变状态、原请求结果、授权或下一步，也不得让 WI 从列表消失。新事务及原请求重放从日志重建投影；读取不依赖投影可写。日志或其原件损坏必须拒绝，不能用投影反向补造。
- 旧消费者读取同一份兼容视图。旧写者不得覆盖新内核已接纳的决定；
  部署必须验证这一写者边界，而不是靠目录命名或本地锁声称排他。

## 日常协作

- list、inspect、continue 在正式入口可见全部原 WI；不存在、来源不可读、
  历史执行信息不全须分别报告，不能把未导入误报为不存在。
- 已有业务归属和确认在新内核中消费。确实缺少的业务决定交回原 Agent，
  Agent 先理解原需求及历史确认，只向人类询问尚未决定的部分。
- 人类决定等待是一种可继续状态，不是异常丢弃，也不意味着接手成功。
  工具结果必须在原 Agent 的同一工作流中可见，不要求用户人工唤醒。
- 决定补齐后继续原 WI 与原业务请求，不能重建 WI、reinit 或重做已完成步骤。
- takeover 与开始业务实施分开；人类要求先理解并对齐时不得自动实施。

## 部署与验收

1. 新内核测试直接读取覆盖生产所有状态及扩展字段的历史样本，保持原始字节。
2. 两个独立客户端操作同一正式格式账本，覆盖并发、重复请求、中断、
   提交未知、旧写者冲突、缓存删除与重建；不得出现第二业务事实源。
3. 标准和轻量流程在新 execute / inspect / resume 上完成，并继承既有决定。
4. 缺少业务归属的 continue 结果交回 Agent；补齐决定后沿原请求继续。
5. Muse 安装回执、实际进程、Relay profile、工具调用均指向被验证的新内核。
   原账本 readback 与历史样本验证通过后，才报告可进行用户渠道 UAT。
6. 原 Telegram 会话、历史、渲染、规范工作区、统一工具链和凭据保留。
   Coevolution 的 lifecycle skill 与 Muse checkout 同步实际入口与语义。

生产 WI550 由人类执行 UAT。部署和兼容测试不得代替人类接手该 WI、
确认其业务归属或开始实现。历史迁移试验账本保持归档，不作为生产依赖。
