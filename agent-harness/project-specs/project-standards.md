# agent-harness 实现与验收规范

## 1. Spec 先行

先完善功能、架构、验收和来源对应，再实现。每项功能有 AH 编号，规定可观察结果、输入/权限、失败语义和验收场景；代码提交说明覆盖哪些条款。新增发现先修订相应条款，不能绕过规格另加恢复状态机。

本项目级 Spec 约束新实现，旧 `specs/` 只提供历史能力来源。文档写完、内部审阅、代码实现、自动验收、安装与真实采用分别标注；不能把设计目标写成已经可用。

## 2. 源码结构

- Python 使用本机 canonical 环境，不建立长期私有 venv。
- 公开 API 有清晰类型与输入/输出契约，静态检查覆盖新代码。
- 领域逻辑不依赖文件系统、网络或进程；内核提交后才可执行外部效果。
- 正常新核心禁止依赖旧生命周期实现。迁移工具单向读取旧格式，不能被正常路径隐式调用。
- 旧命令兼容只做参数和响应转译；不允许旁路写者、双向同步或隐藏旧控制器。
- 一处职责只有一个决定边界；添加新的层必须承担明确职责并退出对应旧责任。

## 3. 新验收取代旧回归

按用户明确指令，旧 `agent-harness/tests/` 全量回归及其覆盖率目标不再是重写版本的前置或发布门禁。可以整体放弃旧套件；不得为了让旧 fixture 通过而复制旧架构。

新测试从 project-acceptance 的场景建立，使用独立配置和目录，不自动继承旧 pytest.ini/conftest/coverage。功能、授权、事实保护和外部幂等语义重新验证，不能因为放弃旧测试就放弃这些能力。

质量由以下证据衡量：全部 AH 义务有实现及对应断言；领域命令合法/非法路径覆盖；同请求/并发/旧执行者性质成立；统一故障矩阵通过；迁移与安装通过；真实入口采用。测试总数和行覆盖率不是完成标准。

## 4. 文档审查

机械检查必须验证 AH/A 标识唯一、需求无未定义验收场景、无孤立必需功能、来源路径与文档链接有效、无伪造通过状态。语义检查核对标准/快捷/升级/返工、迁移、授权、外部未知结果以及完整自重建之间无矛盾。

README 只说明当前可用版本、安装和正常使用；实现未完成前只链接目标 Spec，不替换当前有效用法。work-item-lifecycle 在新入口可用时同步为意图与响应解释，不能搬入内部恢复步骤。

## 5. 用户资产与交付

保留原 WI、成果、人类决定、独立回执和未决操作；代码与测试重写不授权删除生产数据、未提交成果或凭据。只在隔离实验环境注入故障。

正式安装证明精确源码/制品和实际加载版本；每个必需消费者验证真实业务结果。一个节点成功不能宣称其它节点或渠道已采用。旧写者退役通过实际调用和依赖检查证明。

提交和分支使用已授权的受管工作区及正式写入入口。新分支仅隔离实现，不产生新 WI。已授权 rollover 仍保留相同 WI、成果、规格与当前范围；交接材料不得把旧 CI 卡点恢复为主线。
