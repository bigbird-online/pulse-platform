# Native core on TCloud through canonical CD

The approved default-branch source SHA supplies Relay and the native core in one
managed release-writer transaction. The lifecycle skill is pinned to a reviewed
Coevolution main commit. The account canonical Python executes every operation.

Preparation builds from Git objects, seals the core and skill, and replays the
original PULSE production Git ledger. Preparation never replaces the active
program, Relay manifest, channel configuration, session files or business facts.
There is no independent durable native database.

Host workspace scope includes the account's historical managed roots registered
in `config/scl-surfaces.yaml` and the native installer's managed workspace root.
Neither retained conversation state nor measurement bindings may enlarge that
scope or grant WI authority. Existing physical worktrees and transcripts remain
in place. Before activation, the candidate builds the actual retained Pi launch
through the channel's normal identity resolver and launcher. A missing transcript,
out-of-scope workspace or incompatible launch rejects deployment before stopping
Relay. This preflight invokes no model, sends no message and writes no business
state; service health alone is insufficient evidence of a resumable conversation.

For a merge-capable candidate, both TCloud and ownermac prepare the optional
`pull_request_gate` for exactly `bigbird-online/PULSE`,
`bigbird-online/CollaborateWithAI` and `bigbird-online/Oikos`. Preparation resolves
`gh` from the operator's existing deployment toolchain and validates it as an
installed protected executable; missing or unsafe tooling rejects preparation.
The policy retains that provider launcher and the sealed release's `pulse-gh.py`.
Execution uses the existing account authentication through the local control
plane, not SSH fallback or another node's credentials. Compatible predecessor
programs without the merge adapter keep their gate absent.

This placement only enables the existing kernel gate: current holder, generation
and scope, native commit authorship, same-Agent heterogeneous current-flagship
review at high or above, score 85, three-round limit and CI checks are unchanged.
Pi sessions' commits are read from their own Pi records under the same rules
(`project-specs/rewrite-native-operations.md`); the Pi record, the workspace and
the registering Host are on the same node, and enabling the gate proves no
adoption.

Both registered sites compile standalone source bindings through the same
`standalone_programs` / `standalone_profiles` compiler. Executables come only
from Coevolution's maintained `ssot/toolchain/agent-runtimes.json`, including
site overrides, not caller PATH or an ad-hoc provider. TCloud's deployment site
`tcloud` resolves Agent channel aliases against registry host `tcloud-node2`.
Every configured consumer must resolve to a registered Agent; conflicting or
unknown identities reject preparation. The reviewed Relay configuration retains
the node's actual Agent workspace placement, which may differ from its canonical
registry workspace. Shared transport aliases collapse only to that same actor;
two actors claiming one standalone workspace reject preparation.

Standalone CLI profiles bind only those configured physical, account-owned Agent
workspace directories and the account's original `.claude/projects` and
`.codex/sessions` roots. The existing `.pi/agent/sessions` binding protocol is
preserved, not extended into Pi authorship or metering. Account switches and
workspace/source redirects are rejected. Arbitrary CODEX_HOME overrides, copied
rollouts, credentials and fabricated process proofs are not installation inputs.
Native executable ancestry, original session ID/log and original cwd still select
the actor; a plain shell cannot borrow a profile. This installs source identity,
not WI execution authority, holder status, scope or generation.

No managed workspace root is appended to these standalone profiles. A managed
allocation outside the configured Agent workspace still fails native source
selection even if the journal admits it for another operation. Supporting such
an identity mapping would require the kernel's exact current allocation/ownership
facts; directory naming, a global managed root per actor, or copied proof cannot
supply that mapping. This deployment deliberately does not implement it.

TCloud prepares `~/.local/bin/harness-native` pointing only to the canonical
Python and installer-owned `active/harness.pyz`. The existing protected-file Git
consumer transaction also owns this launcher: preparation retains its preimage
without changing it, activation validates all consumers before adopting it,
readback checks exact bytes/mode, and rollback restores the exact original or
absence. Concurrent edits, symlinked entries and unprotected originals reject
adoption rather than being overwritten. ownermac retains its existing cohort.
These are source changes, not an installed-policy repair: bootstrap delivery
still requires the approved default-branch release and an already admitted
native deployment path. A currently rejected session cannot self-admit by
running a new launcher from its workspace.

Activation requires the existing capacity and idle gates and binds actual Pi
consumers to the stable native entry. TG and Feishu may represent the same actor
through different, non-overlapping original session roots. Producer identity
still comes from the actual process and original log; verifier identity remains
independent. No session is started as a deployment check.

The same transaction inventories the account's retained Git guard installations
and replaces their pre-commit/pre-push consumers with the shared native guard.
Installation metadata selects an exact workspace query; only the installed core's
current native holder and journal-bound physical allocation can authorize it.
Legacy environment fields, old controller programs and directory naming cannot
grant or deny the new authority. Preparation preserves private hook preimages;
activation rejects concurrent edits, verifies both installed hooks and their
guard program, and rollback restores the exact prior consumers. Neither hook
migration nor its readback commits staged business changes or starts a session.

Failure restores the exact prior core selection and manifest, then the existing
managed writer restores the prior Relay binding. Core rollback rejects a newer
concurrent selection and replays current facts with the predecessor before any
pointer change. Business logs and authority are never rolled back by deployment.

Readback must prove exact source and bundle, active core, loaded lifecycle skill,
actual process and manifest adoption, shared production ref, historical replay,
and healthy existing channels. Human UAT and bot cutover remain human actions.
